**Implementation return; not deployment approval.** Baseline: the supplied
`quotecore-plus-SA-P1.6-next-phase-handoff-2026-09-26.zip`, agent export `a18f4ab9`.
The original integrated P1.6/P2/P3 fixes are retained. There is no new model choice,
no pricing change and no claim of live P1.7 speed. Start with root RETURN_NOTES.md.

## 1. Objective and acceptance

Retain the proven authoritative retrieval architecture. Move parent/child identity,
business vocabulary, numeric ranking and known repair boundaries into code instead
of paying repeated Luna interpretation/verification calls. Ordinary successful read
turns should need one interpretation and one compound retrieval, with deterministic
presentation when sufficient. Complex explanations still have synthesis; actual
business edits still require the existing requester Confirm button.

This is not a “last backend phase” promise. Live testing decides readiness for UX.
Correct scope, consistent clarification, no false global winner and no mutation
without confirmation take priority over saving one network call.

### Same authoritative scope, no shadow data

The existing 16-source registry/fingerprint is unchanged. Every data query uses the
admitted run, its authenticated company, revision and registered RLS-invoker readers.
The model does not supply company identity, joins or raw SQL. P1.7 retains existing
catalogue entitlement and knowledge gates. Knowledge is NOT enabled by this package.

The new SQL reader executes the same trusted scope helper per invocation. A composite
has two bounded reads, not a persistent permission cache. Each read revalidates in
its own database snapshot. Normal final output access checks remain. A P3 proposal
rechecks the parent relationship in its fresh authoritative snapshot, and confirmation
retains the existing permission/state/proof protocol. No cross-turn cache was added.

## 3. Deterministic composite contract

`resolve_workspace_relationship({selection, presentation})` is registered only when
P1.7 is available. `selection` supplies a fixed relationship, exactly one parent
identity (id, text or current=true), optional child id/text, optional fields and limit.
Parent scope/owner are explicit. Unknown keys/relationships and inaccessible fields
are rejected before querying. Child selection is confined to the chosen parent.

Registered paths:

| Relationship | Child | Name field |
|---|---|---|
| `quotes.components` | placed quote components | name |
| `quotes.areas` | quote areas | label |
| `quotes.customer_lines` | saved customer quote lines | text |
| `quotes.orders` | material orders | supplier_name |
| `quotes.invoices` | invoices | customer_name |
| `orders.lines` | structured order lines | item_name |
| `orders.text_lines` | line-by-line order text | text |
| `invoices.lines` | invoice lines | title |
| `catalogues.rows` | catalogue rows | description |
| `component_collections.components` | reusable library components | name |

Parent resolution uses the existing deterministic ranking/ambiguity rules. A near
tie returns choices; it does not fetch children from an arbitrarily chosen parent.
Child resolution uses a **field-constrained** search. A parent job named “Ridge”
cannot boost an unrelated component as though its own name matched Ridge.

`quotes.orders`/`quotes.invoices` use registered reverse relations. Related predicates
remain EXISTS/semi-joins, avoiding duplicate parents. The new result's relationship
metadata is generated by the service, not accepted from model arguments.

Example read:

```json
{"selection":{"relationship":"quotes.components","parent":{"text":"9th canvas test","quoteScope":"drafts"},"child":{"text":"Ridge"}},"presentation":"open"}
```

Example P3 preparation (the existing tool, NOT a new commit API):

```json
{"selection":{"relationship":"quotes.components","parent":{"text":"9th canvas test","quoteScope":"drafts"},"child":{"text":"Ridge"}},"changes":{"material_rate":25},"quantity_unit":null,"rate_unit":"m"}
```

Use the existing tool's actual changes/units schema. Null unit is only valid under
its original validators; never guess an unspecified rate unit or conflate per-foot
and per-metre values. The wrapper accepts exactly one `component_id` or selection.
A resolved ID is passed with an internal expected parent to P3. A move between
resolution and snapshot refuses preparation. No proposal is created on ambiguity.
The model still cannot Confirm; a choices/navigation tap is not a mutation approval.

## 4. Explicit semantic vocabulary

Normalization is small and deterministic, not an attempt to guess all English.

- Invoice `unpaid` / `not paid` / `not_paid`, or `concepts:["unpaid_invoices"]`, maps
  to `paid_at IS NULL AND status != cancelled`. Drafts are unsent, not automatically
  overdue. Existing extra filters survive. Contradictory paid predicates, negations
  and mixed status lists are rejected rather than guessed.
- Enumerated status case/whitespace is normalized against the existing actual
  quote/invoice/order statuses. Unknown `open`/`due` values are rejected.
- Quote `quote_value` / `saved_quote_total` maps to `customer_total`;
  `current_builder_total` maps to `builder_total`. Invoice `invoice_total` maps to
  the existing total. No new tax/discount/rounding logic is introduced.
- `average` maps to `avg`. Related `natural` search is constrained to exact word
  membership, retaining all text. Names, dates and identifiers are not rewritten.

Authorization and old compiler validation follow normalization. It cannot turn a
hidden field into a visible alias. User scope is never removed to make a plan pass.
A bare numeric name is still not aggressively guessed into an ordinal job name.

## 5. Ranking/rollups and completeness

Numeric primary `orderBy` in rows mode is a value ranking. Aggregate mode continues
count/sum/avg/min/max and groupBy; ordering by metric_N ranks groups. Numeric rankings
require definite population membership, not fuzzy natural suggestions. The engine
and SQL do not let text relevance reorder the numeric result.

The new invoker RPC computes evidence in the same query snapshot BEFORE LIMIT:
`matchedRows`, `groupCount`, `missingValues`, `dimensionCount`, `missingDimensions`,
registered `dimensions`, and `ranked`. Counts use decimal strings. Stored numeric
values stay strings through transport. `_position` and `_tie_count` report rank of
the primary value and all ties, including ties outside the displayed page.

The original bug checked missing values only in returned groups. P1.7 examines all
groups, so a missing value in an omitted group invalidates an otherwise complete
“highest customer” answer. Unknown coverage is a read failure, not assumed complete.
Unlike currencies/units are not compared; the response requests a single dimension.
For ordinary grouped sums, each dimension remains separate as in P1.6.

Derived quote values still use complete bounded inputs and the existing financial
engines, not model math. Population/tie evidence is generated BEFORE slicing the
engine results. >200 quotes, excessive children and payload overflow refuse instead
of presenting a sampled winner. Grouping stored names does not deduplicate people
or merge similarly named components; the result's grouping labels remain explicit.

Limitations: whole-population ranking necessarily inspects matching inputs. It is
not guaranteed cheap just because only five rows are returned. Filter and index
performance must be measured with actual large fixtures. No approximate materialized
summary database, currency conversion or blanket “zero for missing” was introduced.

## 6. Model-loop control

Only tools explicitly marked `retrievalPolicy` use the P1.7 repair allowance. One
batch of invalid/unsupported plans counts as one failed planning round. A second
failed planning round exhausts the allowance and forces tool-free synthesis of the
verified error. Generic repeated calls and existing 5-hop/10-tool hard bounds remain.
Errors preserve the distinction between unsupported capability, empty data, denied
permission, setup failure and oversized work. A timeout remains terminal.

Metadata discovery (`planningOnly`) and one rejected plan may precede a terminal
trusted read. Earlier successful business reads/proposals do NOT become eligible
for this shortcut. Only registered server-produced results can supply terminal text;
final fresh authorization and trusted finish still govern release/accounting.

This is bounded repair, not a guarantee that every request makes one model call.
Complex workflows, genuine disambiguation, a metadata lookup or one repair still
cost additional calls. Telemetry measures that rather than inventing a speedup.

## 7. Component navigation

A placed component target is `{kind:quote|draft_quote,id:parent,focus:{kind:quote_component,id:child}}`.
It is not `kind:component` (which still means library component). Target equality
includes focus, so a card cannot be replayed with another child/stripped focus.

The navigation endpoint's existing stored-card proof is retained. The destination
builder freshly reads the parent, checks Components visibility, reads the exact
child under that parent with the authenticated/RLS client, and rechecks access.
Only known internal routes can be constructed. Blank-entry quotes do not receive
an invented placed-component route. Normal quote summary opening is unchanged.

The only general QuoteCore UI edits are a tiny, optional query/event focus bridge
in the existing builder and expandable row. It reveals already-loaded content,
changes no data, does not confirm a proposal and does not restyle the page. Explicit
navigation events handle query-only/same-page navigation; ordinary rerenders must
not keep snapping back after a manual phase change. Browser verification is required.

the original P1.6 RPC, tables, policies, company flags, quota or business records.

the generated schema-version.ts artifact is normalized to its generator's LF bytes.

Enablement requires ALL: existing assistant/P1.6 company/server gates, compatible
capabilities with version1, and `SMART_ASSISTANT_RETRIEVAL_V17_ENABLED=true`.
No new per-company rollout record is created. Keep the one-company live testing
policy and knowledge/P4 off. Isolated disposable security fixtures are separate
from widening the product rollout; setup requires integrator approval.

With P1.7 off, the assistant uses the old query RPC/compiler/tool set. After a flag
rollback, already-stored focused cards still undergo fresh authorization. Leave
additive metadata/readers installed; do not remove tables or rewrite existing runs.
A function-level statement_timeout is NOT proof of hard caller wall-clock cancellation.
