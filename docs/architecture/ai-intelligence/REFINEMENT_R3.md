## 1. Delivered isolated vertical slice

- `quotation/editor-handoff.ts`: uses a trusted, scoped Phase 5 `approvedHandoff` result and canonical quote ID, returns `customer-edit` locator plus reviewed candidate, no URL invention, no write/send authority. `checkEditorRoundTrip` compares actual canonical post-save rehydration with the exact approved candidate: component copy, quantity text, amounts, visibility/order, scope text with source/version mapping, non-priced visible exclusions, tax lines, totals, contact, currency, profile and no exposed margin. Returns explicit blockers and an attestation hash, not an approval. No replacement renderer or pricing formula. Phase 5 one-to-one component/visible scope copy restriction retained; grouping, discount/overrides and more complex layouts need validated mapping. The adapter must obtain the scoped `ReviewedDraft` wrapper from the real Phase 5 service and re-read current approval and candidate, not accept a browser-crafted object. Round-trip proof is not a proof of actual PDF/public rendering; independently check those artifacts.
- `quotation/lifecycle.ts`: `LifecycleStore` extends the existing transaction concepts and Phase 8 follow-up projection. Server-only unregistered port. `preview` checks canonical saved/reloaded/rendered version, upstream approvals, totals, scope resolution, verified recipient, immutable customer snapshot and attachments. Strict document identity binds quote ID, monotonically increasing version, editor revision, estimate/draft approval digests, round-trip hash, actual render/terms/branding/public document hashes, quote number, currency, total, customer/contact, recipient, sender, email template version, subject/body, final message render hash and selected file name/type/version/content/bytes. 50 MiB per file retained. Exact payload also binds current job/input/policy and canonical events. The private preview is not customer copy. Hub view omits body, token, private IDs/bytes, artifact hashes and receipts; exact render viewer is a server host responsibility.
- Explicit human `prepareApproval` returns a binding; actual trusted receipt minting remains outside the service. Initial and follow-up release require separate exact `send_quote` approvals, with `configure_followups` permission additionally required for follow-up. Neither Phase 5 draft approval nor Phase 8 schedule preview authorizes sending. `enqueue` verifies active receipt and current approver in one transaction, consumes receipt and records one intent keyed by canonical quote/version/kind/sequence, only with explicit reviewed sandbox gate. An exact replay returns existing state; collision or used key is withheld. No provider call inside or outside the transaction. A distinct server worker must claim once, fresh re-read all gates, current requester/approver authority and receipt expiry; claimed intent is not proof of delivery. Last `revalidateClaim` checks again for same worker. Manual cancellation available before claim, even if Intelligence is disabled. Stale claim is cancelled before handoff; a post-claim failed check or crash is uncertain until reconciliation. `markUncertain` does not retry. `reconcile` loads trusted receipt evidence by scope/key/hash/kind, verifies time and unique message ID, handles sent/suppressed/not-sent/unknown distinctly and rejects conflicting terminal receipt. No parallel email sender, direct customer status change, public token creation, or actual send. Intent journal is coordination metadata only, existing canonical message/provider records remain authoritative.
- Tracking: read-only current canonical status (including unrendered drafts), versioned sent/viewed/accepted/declined/revision_requested/withdrawn/expired timeline, historical versus current activity, release state and next action. Current accepted commercial baseline review suggested only with matching accepted-version evidence; otherwise verify accepted version. Revision requests link back to existing revision workflow; no model-generated customer actions, no automatic reopen or overwrite. New reviewed revision uses same quote ID, new version and approval. Uncertain previous delivery blocks release of a new version until reconciled. No independent job or status table. Do not treat `sent` as proof of inbox receipt or a view as customer identity.
- Follow-up: Phase 8 parsers and timing/consent/approved template semantics reused; R3 repeats the required final checks within the same release transaction to avoid a stale two-transaction handoff. Must match exact current sent version, receipt/event and recipient; awaiting response, no cancellation/opt-out/pending follow-up, policy and template exact, canonical rendered message proof, elapsed delay/gap, cap, company-local quiet hours. Customer response/revision/withdrawal/expiry blocks any no-response chase. A fresh human approval and sandbox gate required. No schedule registered or automatic email sent. Reconcile Phase 8 preview and R3 checks into a shared pure predicate in Gavin's integration if appropriate; don't let two policies drift. Adapter must exclude the current R3 intent when deriving external pending follow-up and include unrelated scheduled/manual sends.
- `hub/quotation-model.ts` and `QuotationLifecyclePanel.tsx`: additive unmounted browser-safe projection, status/timeline, delivery history, review blockers, recipient/amount/subject/attachment names, next action, canonical manual editor and activity callbacks. `quotationAttention` provides minimal notification/inbox candidates; no notification transmission or new notification subsystem. Host opens exact scoped rendered document and exact email preview before a human commits; panel does not enqueue, mint receipt or send. It uses existing v2 primitives and remains unmounted; R2 Hub and all normal app files are unchanged. No voice behavior modified. Actual notification channel preferences, real navigation/host callbacks and UX testing outstanding.
- `tests/intelligence/r3.test.ts` and `r3-editor.test.ts`: 37 new test cases, including synthetic complete release/response/revision flow, cross-company/scope/actor, draft-vs-send, exact version/subject/body/attachment/branding/terms/totals, stale revisions, replay, expired/revoked approval, one-time claim, cancellation, post-claim changes, ambiguity, suppression, exact receipts, response before follow-up, policy/time/consent caps and safe view projection. Test fixture uses in-memory atomic clone/commit; it is not a live distributed lock, provider receipt or database security test.
