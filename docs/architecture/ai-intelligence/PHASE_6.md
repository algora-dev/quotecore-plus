# Phase 6 — Isolated email intake and event-origin analysis

Baseline e2209d3e + cumulative Phases 1A–5. Implements a server-domain slice of architecture §§7.4, 8 and Stage 6 plan. No provider, route, mailbox, scheduler, migrations or live worker is registered. Owner has directed experimental integration into a dedicated Intelligence branch, Vercel project and isolated Supabase environment, separate from the normal development/testing/production deployment flow.

## Delivered

- `intake/contracts.ts`: bounded, normalized plain-text email metadata, stable provider/RFC message identifiers, sender authentication indicator from trusted adapter, thread/forward indicators, attachment metadata and digest-bound scan result. 50 MiB per file, existing provisional packet limits (20 files, 150 MiB, 200 pages); body max 32,000 characters/64,000 UTF-8 bytes. PDF/PNG/JPEG only for clean staging. No links fetched, no HTML interpreted, no archive expansion, no executable attachment opened by the domain layer. These are metadata contracts, not MIME decoding, malware scanning or signature verification.
- `intake/service.ts`: authenticated route-scoped transaction port, durable record and replay-safe message dedupe under transactional adapter, collision rejection, quarantine pending trusted scan, flags for unknown/unauthenticated sender, forwarding, repeated attachment, thread revision and duplicate/unsupported attachments. Explicit reviewer link to existing canonical job/intake, review notes and requested deadline. Does not infer customer identity, create jobs or replace document revisions. Reviewer detail retains plain-text subject/body, sender candidate, thread candidates and attachments; daily internal queue contains no email addresses, body or filenames. Queue sorts reviewed overdue deadlines first, then deadline and age; deterministic notification keys for future internal notification adapter. No emails or other notifications sent. All user-facing text remains untrusted data; subject is a scope candidate, not a validated RFQ.
- `schedule` creates a bounded, version-bound event analysis intent only after fresh intelligent-mode admission, company grant, entitlement, exact verified/staged manifest and minimum budget checks. `dispatch` atomically enqueues the existing Phase 1B `Task` shape with stable intent ID and stage/input/policy dedupe; a replay can return the same task, not create another. `preflight` is read-only, not permission to act outside the transaction. No user impersonation; no estimate/quotation/send operations. Prior task/run replacement requires explicit existing archival and revision workflow.
- `intake/event-store.ts`: event-specific wrapper for the existing `IntelligenceService` and `DocumentWorker`. Resolve an opaque task ID through a trusted port on each transaction, re-check current route, worker grant/version/expiry, job/input/policy, staged manifest, event admission, exact task and actor. Validate initial document manifest and reject unrelated task mutation. Existing lease/fence, page budget reservation, provider usage reconciliation and evidence checks remain authoritative. Revocation blocks subsequent transactions (including late results); cannot cancel in-flight transport atomically. Authorized reconciliation must settle held usage and cancel/supersede revoked work through separate control paths. Event task execution must never use an unguarded worker store.
- `tests/intelligence/phase6.test.ts`: 18 tests including serialized fixture race/replay, changed deliveries, authorization, bounds, quarantine, versioning, private queue, grant/entitlement/mode/budget, staged manifest, exact intent/task, revoked and stale dispatch, actual existing Phase 2A worker processing two synthetic pages using a simulated provider and guarded store, and revocation before second page. No real inbound delivery or malware scan tested.

## Integration requirements (Gavin)

1. Keep Intelligence in `feature/quotecore-intelligence` (or agreed branch), dedicated Vercel project and separate Supabase project/storage/test data. Maintain one-way updates from current `development` into experimental branch. No changes to regular testing/production deployment targets or credentials. Do not expose live inbound addresses, customer email, production billing or broad personal mailbox access. Require explicit owner approval of integration, infrastructure and any migrations; no merge back until owner-approved pilot and regression gates.
2. Choose provider-supported inbound or scoped mailbox connector. Existing `emails/`, send-document and webhook surfaces are not general inbound ingestion. Verify ownership, route mailbox to canonical workspace, provider signatures over original request bytes, timestamp, event replay and stable provider IDs before `receive`. Do not trust sender display name or unauthenticated headers. Determine sender authentication and forwarding based on verified transport evidence. Define scoped sender allowlist and human-review fallback. Stream bounded MIME payloads; reject unsupported/oversize messages before allocation, quarantine attachments, enforce mailbox rate/volume/retention limits, handle provider retry acknowledgment only after durable receipt; redact logs. Store original headers/raw message only in access-controlled storage per retention policy. Current normalized contract retains selected headers only; original-header preservation and safe parsing are integration tasks. No provider selected or signature code added here.
3. `IntakeStore` locks exact route and canonical job + company budget/dedupe under trusted time. Authenticate every actor and enforce permissions/RLS; route-specific message uniqueness (provider ID and RFC ID) and company/job/stage/input/policy unique task constraint; atomic job/intent/outbox persistence. Use immutable private storage for quarantined bytes, verify actual hash/size, content signature, malware screening and sandboxed PDF/image parser before `scan`. MIME label alone is not proof. Reject polyglots, bombs, remote references, unsupported attachments, unsafe names and parser timeouts. Do not serve or parse unscanned content in normal app. Scan result projection only from trusted scanner. Duplicate hashes within one packet block; cross-message repeated hashes are review flags; cross-mailbox dedupe policy still needs implementation. Route version change intentionally blocks old record processing; authorized retention/review and re-link flow required. Unknown/ambiguous/forwarded mail always manually reviewed. Notes-only requests, unsupported or duplicate attachments require a manual re-stage workflow; do not silently drop them.
4. Provide explicit draft intake/quote creation and association UI with authoritative customer/contact validation, approval of scope and deadline, and thread/revision conflict handling. Human reviews every message in this first slice, including known senders. Do not assume threads establish identity or replace old documents. Finalize exact verified documents via reviewed storage workflow; canonical job projection must hash initial manifest in envelope attachment order (not scan order), link real upload revision IDs, and enforce task input hash includes staged bytes and source revisions. No job creation, replacement, automatic deadline extraction or RFQ model extraction in this phase. For revised existing quote, prior document-run archival/supersession, dependent approval invalidation and same-job correlation require integration. Review queue/detail must be authorized and render only plain text safely, with reviewer-specific access.
5. Provision explicit revocable route/company worker grants with bounded expiry, worker service identity, intelligent mode, pilot flag, per-stage policy and billing permissions. Do not map existing ordinary entitlement to autonomous permission. `dispatch` is a server-only transactional enqueue; event task must have durable linkage to the intent/route/grant; scheduler resolves opaque ID. `EventJobPort` must load/lock exact intent, route, grant, canonical company/job and authority on every call; recompute staged manifest from immutable original sources independently. Never call existing worker on event task via unguarded store or fabricate a user. Recheck immediately before external IO; no guarantee of atomic cancellation with external provider; abort transport when possible and reconcile uncertain usage separately. Apply concurrency caps, scheduling/lease/retry/dead-letter rules, privacy/observability, kill switch, budget reconciliation and real storage/worker persistence. Pilot tests must prove crash recovery across process boundaries, race-safe queue, revoked grant, source update, RLS and no duplicate tasks/provider calls. The fixture is only process-local and does not prove distributed durability.
6. Existing Phase 2A analysis can run after review/staging without browser interaction once integrated. Brief publication/review, measurement, estimating and quote stages retain their earlier human gates and canonical engines. Do not attempt automatic writes or progression through commercial stages yet. Use internal daily queue as projection, not a new quote status machine. Persist internal notification delivery keys if enabling internal notifications; no external notification transport implemented. No acknowledgment, outbound email, follow-up, billing charge or customer quote send; separate later authorization and exact payload approval required.
7. Run AGENTS.md full build/type/takeoff/topology/calibration/precision/billing guards in isolated project before any pilot; validate real inbound signed test mail, malicious/unsupported payload, duplicates, forwarding, revisions, storage/quarantine, grant expiry, scheduler, queue, worker recovery and real roofing packet. Do not enable unattended processing until prior stages are live-tested and owner approves pilot. Keep all manual workflows and default-off policy. No protected files or dependencies changed.
