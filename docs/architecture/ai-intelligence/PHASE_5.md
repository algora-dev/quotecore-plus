# Phase 5 — Intelligent quotation preparation (isolated implementation)

Baseline e2209d3e; additive to 1A, partial 1B, 2A, 2B, 3 and 4. This is a server-domain preparation layer, not a registered live feature. Follow ARCHITECTURE.md section 10.2 and the Phase 5 implementation-plan acceptance criteria. The existing customer quotation editor, template tables, branding and unified sending services remain authoritative. No new generator, price library, send ledger or database table is implemented here.

## Delivered

- `quotation/profile.ts`: strict company-scoped projection of the existing branding template plus approved presentation choices, editable create/update proposal with explicit before/after and changed fields, digest-bound approval validation. No save, memory activation or silent learning. Header/branding and footer/legal terms are preserved verbatim. An approval is trusted only when loaded by the server and the approving role is still authorized.
- `quotation/draft.ts`: validates a current customer quote snapshot, confirmed single recipient, editability, currency, component mapping, explicit scope wording linked to every current estimate disposition, and approved visibility. Uses existing `computeQuoteTotals` and `computeTaxLines`. Checks each component amount, canonical customer subtotal, customer total and canonical builder total independently. Reports the exact tax breakdown, changed document fields, changed/added/removed component fields and previous total. Draft and its dependencies are hashed. No prices, terms or prose are inferred from private evidence. Output is a private editor candidate (includes internal IDs); it is NOT a customer document or outbound payload. Never serialize it wholesale into a PDF/email; existing editor/renderer must apply visibility and project only customer-safe fields.
- `quotation/service.ts`: unregistered server-only QuoteStore transaction contract and preparation service. Checks feature gate, entitlement, authenticated actor and job, estimate review/pricing permissions, current analysis task, current brief/manifest, no active analysis, current estimate reconciliation and exact Phase 4 approval. Reconstructs the Phase 4 preview digest using original request actor and current snapshot; requires active matching receipt and current estimate approver. Requires current profile approval digest and approver. PrepareApproval returns an exact `prepare_quote` binding; approvedHandoff re-reads all state and checks a real active matching receipt, current authority and exact proposed draft. It never writes, saves, consumes receipts, generates tokens, sends or authorizes sending. Repeated read-only handoffs cannot trigger external action. Receipt minting is not implemented; integration must use trusted human approval. Receipt lifecycle semantics: this isolated gate deliberately requires an active estimate-review receipt; if integration consumes a receipt while creating an estimate, Gavin must define a separate durable approved-estimate attestation (not simply accept consumed receipts).
- `tests/intelligence/phase5.test.ts`: 15 tests extending the synthetic document-to-verified-measurement-to-reviewed-estimate fixture into a quotation preview and simulated receipt check. Covers changed profile/terms, visibility, amount/currency discrepancies, scope coverage, stale estimate and draft, invalid/revoked/expired approvals, contact identity and verification, permission/scope boundaries, line diffs and absence of side effects. Test-only receipts are not evidence of a real approval workflow.

## Integration map (read-only source findings)

1. `app/(auth)/[workspaceSlug]/customer-quote-templates` and customer-edit `CustomerQuoteEditor.tsx` are the existing template and editor surfaces. The branding template loads company name/address/phone/email/logo/footer text, not an entire intelligent quoting profile. Store approved presentation preference/version/approval metadata via an authorized extension (schema not approved); avoid duplicate canonical templates. Add profile proposals to existing create/update editor workflow after owner approval. Bind approval to the exact canonical content, including approved logo identity/content or revision, and recheck authorization. Logo URL syntax alone is not authorization, URL safety or content integrity.
2. `app/(auth)/[workspaceSlug]/quotes/actions.ts` `saveCustomerQuoteLines` checks company and calls `replace_customer_quote_lines` RPC to atomically replace lines. It separately updates flags and can assign quote numbers; editor `performSave` also saves branding/taxes/margins in parallel. Do not invoke these methods automatically or assume these multiple operations form one atomic approval transaction. Map each verified estimate line ID to real quote_component_id, and preserve `lineType:'component'`, reviewed text, quantityText, amount, showPrice/showUnits/isVisible/includeInTotal and order; obtain existing stable line IDs, quantity, margin and unit metadata through canonical editor. Confirm round-trip editor hydration/recalculation does not change amounts/quantities. Map every scope entry (including exclusions) to explicit visible customer copy using existing editor mechanisms without adding to total; validate that the final rendered version includes the reviewed scope and exact footer. Do not replace lines on save without explicit user review. Existing `QuotePreview.tsx` and canonical PDF/acceptance rendering remain authoritative.
3. `app/lib/send-document/adapters/quote.ts` computes customer total from customer_quote_lines where include_in_total is true plus quote tax lines (or legacy rate fallback). This is different from builder subtotal. For this slice the trusted adapter must independently compute the proposed customer totals using the canonical editor rules before projection; reject unsupported legacy tax or custom line shapes, mismatched rounding and stale persisted totals. Canonical existing `app/lib/pricing/engine.ts` and `app/lib/taxes/types.ts` are reused; strict floating-point tolerance 1e-7 matches Phase 4, not a new currency rounding policy. Reconcile current editor/accept/PDF/sending totals, including tax labels and currency formatting, with full real-world cases.
4. `QuoteStore` must authenticate actor, verify same-company membership and all quote/component/customer/contact/template joins, enforce permissions and feature/entitlement gates, lock/load a consistent job+pricing+customer snapshot and fresh receipts and authority. Snapshot completeness/recipientVerified/approval metadata are trusted server projections, not client assertions. Contact syntax validation does not verify ownership or delivery. Only approved editor wording and confirmed scope may populate copy; no model writes legal terms. Data is private; escape user copy in existing renderers and validate attachments/branding assets.
5. A distinct final SEND gate is still required: bind canonical persisted quote revision, final rendered content and file hashes, approved terms, branding/assets, exact recipient(s), subject/body, attachments, sender identity, policy, estimate and quote approval versions and current quote status. Re-read all immediately before action; use explicit separately authorized `send_quote` approval and atomic receipt consumption/idempotent outbox with the existing unified pipeline. ## Provisional decisions and scope limits

- First slice is one visible customer component line per verified estimate line, no grouping, hidden total, line suppression, discount, custom allowance, alternate price, override or legacy tax fallback. Approved visibility may hide individual prices/quantities but not scope or total. Priced quantity text is an explicit candidate and may include allowance/waste; confirm appropriate customer-facing quantity in editor. All scope dispositions require explicit reviewed wording, including non-applicable/resolved entries; internal disposition reason/evidence/financial costs are not copied. Grouping, structured legal/payment fields, email templates and follow-up policy, conversational onboarding and learned company defaults need later owner design and integration. Job overrides must get separate approval; no permanent mutation.
- Profile approval, quote approval, durable estimate approval and verified customer data are simulated by a fixture. The existing database has no approved intelligence schema changes here. No profile persistence, UI mount, real draft creation, final document rendering, sending or deployed application workflow. The design deliberately keeps manual operation and default-off flags intact.
- Real roofing pilot, visual analysis/OCR, full application build and regression suite, live RLS/tenant isolation, permissions, entitlements, distributed concurrency, worker runtime and billing still pending from previous phases. No actual customer or production data; no credentials/DB/network/app run. Retain 50 MiB file cap.
